## 1. 编排与可靠性（对标“Agent 编排与可靠性”） ✅

**问题与量级：** 上游 `StandardPipeline` 一个镜头失败就导致整片失败；状态只在 `finalize()` 落盘，没有可恢复的中间态；唯一的恢复手段是整片重跑，已经成功的镜头要重复付费。
证据：`tests/test_baseline_reliability.py`，4 条现状测试。

**诊断：** `FakeFrameProcessor` 逐调用记账，记录每次调用的镜头、尝试次数、结果，以及这次失败是否注定发生（futile）。

**故障模型（模拟器）：** 每次调用按概率失败，故障类型包括超时、429、审核拒绝、输出损坏。审核拒绝按 prompt 版本保持“粘性”，改写后有 70% 概率通过。另有 2% 的镜头输入本身无效，永远不会成功。

**排除假设：** 实验设置为 500 条视频、每条 5 个镜头，每个策略给相同的恢复预算（1 次初跑 + 2 次恢复），每条视频的故障流按种子配对。下表为故障率 30% 时的结果：

| 策略 | 完成率 | 每条成片调用数 | 重复付费/条 | 无效调用/条 |
|---|---|---|---|---|
| S0 上游单次 | 16.8% | 16.23 | 0 | 0.06 |
| H1 上游 + 整片重跑 | 34.6% | 18.79 | 1.25 | 0.43 |
| H2 + 统一镜头重试×3 | 66.8% | 15.65 | 0.99 | 3.58 |
| **FULL** | **82.4%** | **9.13** | **0** | **0.67** |

- H1 被否定：完成率仍只有 34.6%，每条视频还重复付费 1.25 次。
- H2 被否定：完成率提升了，但每条有 3.58 次注定失败的调用。
- FULL 对 H1：配对 McNemar，FULL 独有完成 240 条，H1 独有完成 1 条，p = 1.4e-70。FULL 对 H2：78 比 0，p = 6.6e-24。
- 故障率 10% 时：FULL 完成率 86.8%，H1 为 77.2%，S0 为 54.8%。

**消融（从 FULL 各去掉一个机制，故障率 30%）：**

| 去掉的机制 | 完成率 | 每条成片调用数 | 重复付费 | 无效调用 | 结论 |
|---|---|---|---|---|---|
| 审核拒绝时改写 prompt | 82.4 → 67.2% | 9.13 → 12.17 | 0 | 0.67 → 1.67 | 对完成率贡献最大 |
| 检查点 / 断点恢复 | 82.4 → 81.0% | 9.13 → 12.45 (+36%) | 0 → 1.68 | — | 主要贡献是省钱 |
| 错误分类（改为统一重试×3） | 82.4 → 88.8% | 9.13 → 9.39 | 0 | 0.67 → 1.31 (+95%) | **是取舍：** 分类用约 6 个百分点的完成率，换来无效调用减半 |
| 镜头隔离 | 82.4 → 81.2% | 9.13 → 8.52 | 0 | 0.67 | 串行执行下无可测收益，价值在并行时的延迟（未测） |

**崩溃恢复：** 200 次随机位置的进程终止后恢复，FULL 重复付费 0 次，上游整片重跑共 401 次。

**工程防护：** 错误分为 4 类，各有重试策略：指数退避加抖动、审核拒绝先改写再重试、输入错误不重试。另有熔断器（连续失败后打开，半开探测；打开期间镜头保留为待处理，不付费）、SQLite WAL 检查点、文件丢失时自动重新生成。
代码：`pixelle_video/reliability/`；测试：`tests/test_reliability.py`；数据：`benchmarks/results/reliability_ablation.json`。

**❗写进简历前还差一步：** 故障类型的比例目前是占位值。需要用真实视频生成 API（Seedance 或 Kling）跑 50–100 次，统计真实的错误分布，替换 `FaultProfile.mix` 后重跑本实验。之后才能写“基于真实错误分布的故障注入”。在此之前只能写“模拟故障注入”。

## 4. 安全治理与服务化（对标“安全治理与服务化”） ✅ 服务化 / ⬜ 内容安全

**问题：** 上游 `api/tasks/manager.py` 的任务管理器只存在内存里（注释写着“can be replaced with Redis later”）。服务一重启任务就丢，无法多 worker 部署，重复提交会重复生成。

**实现**（`pixelle_video/serving/`）：
- **幂等提交：** 一个 Lua 脚本原子完成“检查幂等键 → 建任务 → 入队”；同一个键带不同请求体返回 409（Stripe 语义）。
- **可靠队列：** `BLMOVE` 把任务从队列移到处理中列表，worker 持有带 TTL 的租约并心跳续期；租约过期后由回收器（Lua 原子操作）放回队列，交给 `ReliablePipeline` 按同一个 task_id 断点恢复。
- **分布式限流：** 每个供应商一个令牌桶，用 Lua 原子扣减，时间取 Redis 服务器的 `TIME`，不受 worker 之间时钟偏差影响。
- **进度推送：** 镜头事件写入 Redis Stream，SSE 用 Stream ID 作为事件 ID，断线后凭 `Last-Event-ID` 续传，不丢也不重复，任意 API 副本都能接续，不需要会话粘滞。
- **HTTP API v2：** `POST /v2/videos`（必须带 Idempotency-Key）、`GET /v2/videos/{id}`、`GET /v2/videos/{id}/events`（SSE）、`POST /v2/videos/{id}/resume`。

**压测**（真实 redis-server 7.0，`benchmarks/serving_bench.py`，数据在 `benchmarks/results/serving.json`）：

| 场景 | 无防护基线 | 本方案 |
|---|---|---|
| 幂等风暴：50 并发客户端 × 5000 次提交，500 个键 | 建了 535 个任务（35 个重复），7.1k 次/秒 | **建了 500 个任务（0 重复）**，5.9k 次/秒 |
| 混沌：200 个任务、8 个 worker，随机杀 worker | 被杀 40 次，重复付费 78 个镜头 | **被杀 35 次，200/200 完成，重复付费 0** |
| 限流：16 个 worker，令牌桶 20/秒、容量 5 | 1 秒峰值 240 次 | **1 秒峰值 25 次**（= 理论上限），平均 20.4 次/秒 |

测试：`tests/serving/`，12 个，跑在真实 Redis 上。覆盖幂等冲突、租约过期回收、接管检测、跨客户端共享令牌桶、Last-Event-ID 续传、worker 崩溃接管，以及 HTTP 契约。

**还没做（内容安全，对标“361 条攻击 0 得手”）：** 生成前做规则加 LLM 两层审核预检。构造约 100 条会触发审核的 prompt 和约 200 条正常 prompt，报告真实 API 拒绝率下降多少、合法 prompt 误拦多少。需要真实 API，留给你做。
另外还需要配 GitHub Actions CI，CI 环境要装 ffmpeg 和 redis-server。
